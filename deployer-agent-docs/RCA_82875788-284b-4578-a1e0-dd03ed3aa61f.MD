# RCA — Redeploy failed at pull_source (missing backend/.env)

## Problem
Redeploy of `dupe-app` fails at the **pull_source** step. Two independent runs reproduced the exact same error:

- run `82875788-284b-4578-a1e0-dd03ed3aa61f`
- run `9e27ece2-1f52-4451-a926-2d6cebc40c16` (fresh re-pull, force_repull=true)

Error (identical on both):
```
pull_source: activity error ... prepare build context: read envs:
read env file backend/.env:
open /tmp/agent-env-.../app/backend/.env: no such file or directory (PathError)
```

## Root Cause
The `pull_source` step copies `/app` from the preview pod and then reads `/app/backend/.env` to cache its environment variables as the fallback tier used later by `write_secrets`. The file **`backend/.env` does not exist** in the preview pod, so the step fails before the build context is assembled.

This is a preview-environment / source state problem, NOT a manifest or infrastructure problem:
- Prior redeploys on this same deployment succeeded (e.g. `b096b30c` at 05:40, `417f8021` at 04:58), which means `backend/.env` was present before and has since been removed/lost from the preview pod.
- The error is a definitive `PathError: no such file or directory`, reproduced on a fresh re-pull — not a transient copy race.

## Evidence
- `describe_deployment_state`: active run is a healthy rollback (`dc5cc149`); the two failed runs both terminate at `pull_source` with the backend/.env PathError.
- `spawn_eph_pod` for the failed run returned `eph_source_access_failed` — expected, because pull_source never produced/uploaded a source zip (it died before build-context prep).
- Resume with `force_repull=true` produced the same missing-file error against a newly pulled checkout.

## Fix (handoff to E1 / main agent)
Restore `/app/backend/.env` in the preview environment, then redeploy. The FARM template expects at minimum:
```
MONGO_URL=...
DB_NAME=...
```
plus any custom keys the app uses. Even an otherwise-empty `backend/.env` will let `pull_source` proceed (production SYSTEM keys like MONGO_URL/DB_NAME are regenerated by the platform during `write_secrets`; custom keys are carried forward from the last successful production run).

Once `backend/.env` exists again in the preview pod, re-trigger the deploy — the remaining steps were unaffected.
